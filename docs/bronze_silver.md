## Local validation

Requires Python 3.11+ and `pip install -r requirements.txt`.

```powershell
python scripts/bronze_silver.py --stage-bronze
python -m unittest discover -s tests -v
```

Local Bronze stores unchanged bytes at `data/bronze/<sha256>/<filename>`.
Existing matching snapshots are reused; conflicting bytes fail validation.
The quality report is `metadata/silver_quality_report.json`. Local validation
prepares typed data in memory; it does not create Silver Delta tables.

## Fabric layout and execution

Bronze stores the four manifest CSVs at `Files/bronze/kaggle/`, with
source_manifest.json, schema_contract.yaml, profiling_summary.json and
categorical_profile.json in `Files/metadata/`. Silver stores the validation
module at `Files/code/bronze_silver.py`.

`NB_EV_Bronze_To_Silver.Notebook/` contains the Fabric Git item. Its source
and the importable `notebooks/NB_EV_Bronze_To_Silver.ipynb` are generated by
`python scripts/build_fabric_notebook.py`; edit `scripts/fabric_silver.py`
and rebuild instead of editing generated files separately.

### Run after pulling the Azure DevOps changes

1. In `WS_EV_Analytics`, open Source control. If `LH_EV_Silver` appears under
   local Changes, commit that newly created Lakehouse to preserve its Fabric
   metadata before updating. Do not discard it or create a second Silver Lakehouse.
2. Select **Update from Git** to bring in `NB_EV_Bronze_To_Silver`.
3. Open the notebook and verify **LH_EV_Silver** is its default Lakehouse.
   The notebook reads Bronze through its explicit OneLake URI.
4. Select **Run all**. CSVs and profile metadata are copied to temporary driver
   storage for hash validation, then Spark reads Bronze and writes Delta to Silver.
5. Confirm the last output says `status: published`. Inspect the three table
   names and row counts: train 668,665; test 286,571; original_reference 10,000.
6. In Silver, retain `Files/quality/<run>_published.json` as the success marker.
   A validation report alone does not prove table publication succeeded.

If Git update is unavailable, import the generated `.ipynb` instead; do not
both import and Git-sync it, which would create duplicate notebooks. Commit
any Fabric-side item changes through Source control after running.

The notebook checks hashes, file sizes, exact headers, counts, required fields,
numeric parsing, integer bounds, categories, primary keys, target distribution,
train/test key separation and submission/test key order before publishing.
Numeric profile ranges produce warnings rather than invented business rules.
All four files must match the pinned source manifest.

Silver uses separate versioned Delta tables for train, test and original_reference.
`sample_submission` is an auxiliary input, never training data. Original Buyer_ID
stays a string. Numeric business values use decimal(18,4); integers use int/long.
Original labels remain Yes/No, with `will_buy_ev_flag` = 1/0 for labeled sources.
Test has neither target column. Lineage includes source, file, checksum,
processing timestamp and source-prefixed record key. No rows are deduplicated,
imputed, resampled or combined across sources.

Original-reference nulls are retained: income 178, commute 181, environmental
concern 184. Contract v2 records these profiled exceptions; train/test remain
non-nullable. The current pandas validation implementation mirrors this contract;
future contract changes must update validation and tests together.

Every run creates new tables and checks written counts. Only a run with a final
`Files/quality/<run>_published.json` marker is complete. Delta transactions apply
per table; a failed run can leave partial tables but no success marker. Reruns
create a new version rather than appending duplicates or replacing prior data.
Driver-side pandas validation is sized for this snapshot, not large-scale growth.
